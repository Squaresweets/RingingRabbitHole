This is all of plain bob doubles. To share the method with someone else in this form would require communicating quite a lot of data, so lets think of ways to compress it down. We found out in the first episode that the movement of the bells in each lead is the same, so to recreate the whole method we only need to share the first lead. There isn't much point in sending bell numbers here, as we are only interested in how the bells move in the first lead. To store the way these arbitrary bells move we can split this grid view into all of the changes and encode them each individually.
Looking at each change, notice how they are made up of crosses and lines. Each line represents a bell making a place, and if a bell isn't making a place it is swapping positions with an adjacent bell. An intuiative way to store a change is thus to store in which positions places are made. For example, this change would be stored as 1 2 5.
We can apply this encoding to every change in the first lead, and concatenate them to get a much more efficient representation of the method.

Something I haven't talked about yet is symmetry. This is a topic I will cover further in a future video, but in short many methods have some form of palindromic symmetry. This means that if we look at a singular lead, ignoring the next lead head, we can read this lead backwards and still get the same lead. This means that we only need to store one half of this lead and then flip it to get the rest. In terms of changes, if we have a palindromic sequence of changes such as these, we only need to store up to the middle change, as the rest can be infered from the first half. This gives us another trick to compress our notation, we only need to store half of the notation. To expand it to the full notation you just have to take all the notation up to the last change before the comma, flip it, and put it after the comma. You technically have to do this to both sides of the comma, but since there is only one change on the right hand side we do nothing. A minor point is that by itself this isn't enough to generate a method, for example this same notation could generate any of these methods, so you also need to store the stage alongside the notation. When using more than 9 bells we start using the alphabet instead of numbers. Eleven and twelve are E and T, and then we start from A excluding any we have already used. We also exclude I so as not to confuse it with 1.

Notice that for changes on an odd number of bells there is no way to have no places, however on an even number of bells you can. To show that no bells change places we could use this notation, however we instead use an x to represent a cross change. Notice how the full stops around the cross are infered as the x represents an entire change. Notice also that if we have a place in seconds place we always have a place in firsts place, so it is possible to let the first place be implied. This also works at the back. If after all the places in the notation there are an odd number of positions left you know there must be one more place, and it is assumed that this place is at the back. Thus, this change can be written as 1 instead of 15. Places at the front and back are known as external places, and internal places can also be implied, however this is less common due to ambiguity.

Describing calls is simple with this notation. When a call occurs, it overrides a small amount of place notation at the end of a lead. The amount of notation and the position where these changes occur change from method to method, but most of the time, it is one piece of notation changed at the lead end. For plain bob doubles, a bob changes the “125” change to a “145” change, and a single changes it to a “123” change.

Place notation can also be expanded to work with jump changes, however that is beyond the scope of this video. I have put a link in the description if you are interested.

The type of notation shown in this video is very common, however there are quite a few variations. One example is microSIRIL which uses dashes instead of xs, includes the lead head code at the start and uses an ambersand to represent the start of a symmetric section and a plus to represent the start of a non symmetric section, with sections seperated by spaces or commas. The lead head code is just a way of classifying the lead head of the second lead.

This is a plain lead of plain bob doubles. It’s a lot of numbers, but believe it or not this whole method can be encoded with just these numbers:
5.1.5.1.5,125
This is known as place notation and it plays a vital role in how methods are stored and shared. But how does it work?
First, lets examine the first lead of our method. Between each row, certain pairs of bells swap and certain bells stay in the same position. In the first change you can see that the bell in fifths place stays in the same place, while the other bells swap around, thus the place notation for this change would simply be “5”. For the next row the bell in firsts place stays in the same place and thus the place notation for this change would be “1”.

Let’s fill in the rest using this pattern. Since the bells are just plain hunting, this is pretty simple up until the change at the lead end. Here we instead have 3 bells stay in the same place, the bell in 1st, 2nd and 5ths place, so we write 125 for the notation.
So here is the place notation for this method written out in full. A clever trick is that methods with palindromic symmetry have the same notation reversed after the center change, which means that half of this notation is redundant. We can instead write it like this. To expand it to the full notation you just have to take all up to the last change before the comma, flip it, and put it after the comma. This gets us back to what we had before. Since every lead of a method is the same just with different bells, describing the first lead is sufficient for us to generate the entire method.
